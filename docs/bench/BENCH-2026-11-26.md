## After: word-sized texel reads (same day)

The shader read every byte of a texel with its own 32-bit load. It now reads 16-bit values and RGBA8
texels as whole words (the same values, so GPU output is unchanged and the GPU-vs-CPU tests still pass).
Iris Xe clocks swing with heat and power state, so this is an A/B of two builds, run alternately three
times, each figure the median GPU time (timestamp queries) over 15 frames:

| | B1 4K, 3 layers | B2 6K → 4K | B3 photo |
|---|---|---|---|
| Byte reads (before) | 37.1 / 48.3 / 44.6 ms | 20.8 / 20.9 / 21.4 ms | 16.3 / 12.6 / 15.2 ms |
| Word reads (after) | 32.5 / 29.9 / 29.1 ms | 20.1 / 20.9 / 20.9 ms | 13.5 / 16.2 / 12.8 ms |

B1 is about 30% faster; B2 and B3 don't change. The first table's B1 GPU time (60.5 ms) was a single
frame on a hot GPU, not comparable. Single-frame GPU times varied from 24 to 44 ms in back-to-back runs,
which is why `--bench` now reports the median of 15.

## Later the same day: zero-weight taps skipped

`Kernel.inc` no longer fetches a bilinear tap whose weight is exactly 0. A picture placed 1:1 on the canvas reads
one texel instead of four (each with its own four chroma taps). The output is bit for bit the same: `tst_gpu` shows
max |Δ| 0 against the CPU on Iris Xe and lavapipe.

| | Before | After |
|---|---|---|
| B1 compose 3840x2160 CPU | 381.72 ms | 132.94 ms |
| B1 compose 3840x2160 GPU (GPU time) | 63.22 ms (60.49) | 16.31 ms (6.27) |
| B1 compose+NV12 GPU | 72.92 ms | 26.38 ms |
| B2 compose 6016x3384 → 3840x2160 GPU | 26.27 ms | 43.27 ms (37.98); scaled, so no taps are skipped; the difference is run-to-run noise on a laptop GPU |
| B3 photo layer per frame GPU | 28.14 ms | 22.10 ms (13.55) |

The wall time is now mostly upload and readback (16 ms against 6 ms of GPU time), so a swapchain and DMA-BUF
import are where the next gain in the preview is.

**B6 export, a correction.** The `h264_vulkan` export above (0.39x realtime) produced wrong colours. Intel ANV's
Vulkan encode keeps luma but scrambles chroma, and ffmpeg's own CLI does the same. Exports now check an encoder
before using it and fall back to libx264 (0.08x realtime at 4K60) on this machine. VA-API encode (`intel-media-va-driver`
/ iHD) would be the fast path here; it isn't installed on this machine.

## With VA-API (intel-media-va-driver) and DMA-BUF import

Two runs each; the GPU's clocks vary between runs on this laptop.

| | Before | After |
|---|---|---|
| B4 decode 4K HEVC 10-bit, hardware | 97 fps (Vulkan Video, downloaded) | 262–270 fps (VA-API, DMA-BUF; 33 fps if downloaded instead) |
| B4 decode 4K60 H.264, hardware | 152 fps (Vulkan Video) | 271–272 fps (VA-API, DMA-BUF) |
| B1 compose 3840x2160 GPU, wall | 35.9 ms with DMA-BUF off | 26.5 ms with DMA-BUF on |
| B6 export 10 s 4K60 H.264 | 122.8 s (libx264; h264_vulkan scrambled colour) | 22.9–27.3 s (h264_vaapi, colours right) |

The very first VA-API decode on the machine ran at 4 fps: the driver's one-time warm-up. Every run after it was
at full speed.
